## Наблюдаемое состояние на 27 ноября 2026 года

Включены правила защиты `main` и релизных тегов `v*`. Для `main` обязательны pull request и успешные проверки `test` и `visual` от GitHub Actions; требуется актуальная база и закрытые обсуждения ревью. Удаление и принудительная перезапись `main` запрещены. Изменение и удаление существующих релизных тегов запрещены; создание новых разрешено. Обязательных одобрений второго участника нет. Списки обхода правил пусты.

- [Правила main](https://github.com/0w1Max/commando-activity/rules/28206297): **Active**, только `refs/heads/main`; проверки поступают от GitHub Actions с app ID `15368`.
- [Правила релизных тегов](https://github.com/0w1Max/commando-activity/rules/28206421): **Active**, шаблон `refs/tags/v*`; создание тегов не ограничено.

Настройки rulesets проверены через API GitHub 27 ноября 2026 года. Скриншоты GitHub, предоставленные владельцем в тот же день, подтверждают включённые Secret Protection, Push protection и Private vulnerability reporting в `0w1Max/commando-activity`. Secret scanning показывает **0 открытых уведомлений** в репозиториях игры и профиля. Это датированное наблюдение за уведомлениями, не доказательство отсутствия любых возможных секретов.

Репозиторий профиля `0w1Max/0w1Max` описывается отдельно: его список rulesets пуст, правила веток профиля в рамках этой работы не включались. Скриншот профиля подтверждает 0 открытых уведомлений Secret scanning; переключатели Secret Protection, Push protection и приватных сообщений для профиля отдельно не проверены.

Скриншот настроек продукта также показывает **Off** для Dependency graph, Dependabot alerts и Dependabot security updates. Документ не заявляет, что эти функции включены; существующее обновление версий через Dependabot — отдельный механизм.

Подготовленные JSON ниже — **выключенные заготовки**, не включённая защита. Они не добавляют обходы правил и не меняют учётные данные. Для новой установки сначала проверьте целевые ветки/теги. GitHub поддерживает импорт JSON через Settings → Rules → Rulesets → New ruleset → Import a ruleset; названия элементов могут меняться.

## Повторное использование заготовок и проверка изменений

1. Сохранить/экспортировать прежние настройки. Импортировать одну заготовку именно в репозиторий из таблицы и проверить целевые ветки/теги и правила.
2. Для `main` продукта убедиться, что имена проверок — ровно `test` и `visual`. Сейчас их запускает GitHub Actions с app ID `15368`. Не требовать `release`: эта задача выполняется после слияния, а не на PR.
3. Выбрать **Active** и сохранить проверенный ruleset. Состояние **Disabled** ничего не защищает. После сохранения проверить публичную страницу Rules и флаг защиты ветки.
4. Перед включением правил профиля убедиться, что `output` уже создан. Не добавлять туда PR, подписанные коммиты, одобрения и запрет обычных обновлений: публикация пишет непосредственно через `GITHUB_TOKEN`.
5. После включения проверить нормальный PR продукта, возможность создания нового релизного тега и успешное обновление профиля. Не пробовать удалять рабочий тег или ветку ради теста.

Одобрение второго человека не требуется: владелец может слить свой PR после проверок. Широких исключений для администратора/приложений нет. Первый релиз после включения правил проверит совместимость целиком; проверка структуры JSON этого не заменяет. Если правило мешает разрешённой работе, нужно разобрать точную причину и исправить правило, а не выключать всю защиту.

## Другие административные настройки

- Secret Protection, Push protection и приватные сообщения продукта включены по датированным скриншотам владельца выше. Перед фиксацией будущих изменений проверять текущее состояние в Settings → Advanced Security; файл политики сам по себе ничего не включает.
- Для приватного сообщения используется Security → Advisories. Скриншот настроек владельца подтверждает включение; отдельная кнопка в интерфейсе исследователя независимо не проверялась. Тестовые сообщения и настоящие секреты не отправлялись.
- Dependabot alerts и security updates показаны как Off на скриншоте продукта. Настроенные PR обновления версий и `npm audit` не означают включённых уведомлений GitHub. PR зависимостей проходят обычный CI; обновления не одобряются автоматически.
- Ограничивать workflow-токен на уровне задач; календарный токен оставлять только для чтения. Не расширять права PAT ради обхода правила ветки. Значение, срок и права токена в этом ревью не просматривались.

Поддерживать [SECURITY.md](../../SECURITY.md) и русскую версию в соответствии с наблюдаемыми настройками. Активация rulesets продукта проверена через API; сведения только по скриншотам явно помечены. Обычный PR документации проверяет защищённый путь слияния. Новый релиз и запуск публикации после активации — отдельные проверки; документ не заявляет, что они уже выполнены.
