[English](../en/REPOSITORY_SECURITY.md) · **Русский**

## Наблюдаемое состояние на 27 ноября 2026 года

Списки rulesets обоих публичных репозиториев пусты. API веток сообщил `protected: false` для `main` продукта и `main`/`output` профиля. Детальное чтение старой защиты интеграция отклонила с `403 Resource not accessible by integration`; это ограничение доступа, не положительный результат проверки безопасности. Настройки уведомлений об утечках, push protection и приватных сообщений об уязвимостях не проверены. В облачном браузере нет входа; административные настройки не изменялись.

Подготовленные JSON ниже — **выключенные заготовки**, не включённая защита. Они не добавляют обходы правил и не меняют учётные данные. Каждую нужно проверить и включить в указанном репозитории. GitHub поддерживает импорт JSON через Settings → Rules → Rulesets → New ruleset → Import a ruleset; названия элементов могут меняться.

## Как применить и проверить

1. Сохранить/экспортировать прежние настройки. Импортировать одну заготовку именно в репозиторий из таблицы и проверить целевые ветки/теги и правила.
2. Для `main` продукта убедиться, что имена проверок — ровно `test` и `visual`. Сейчас их запускает GitHub Actions с app ID `15368`. Не требовать `release`: эта задача выполняется после слияния, а не на PR.
3. Выбрать **Active** и сохранить проверенный ruleset. Состояние **Disabled** ничего не защищает. После сохранения проверить публичную страницу Rules и флаг защиты ветки.
4. Перед включением правил профиля убедиться, что `output` уже создан. Не добавлять туда PR, подписанные коммиты, одобрения и запрет обычных обновлений: публикация пишет непосредственно через `GITHUB_TOKEN`.
5. После включения проверить нормальный PR продукта, возможность создания нового релизного тега и успешное обновление профиля. Не пробовать удалять рабочий тег или ветку ради теста.

Одобрение второго человека не требуется: владелец может слить свой PR после проверок. Широких исключений для администратора/приложений нет. Первый релиз после включения правил проверит совместимость целиком; проверка структуры JSON этого не заменяет. Если правило мешает разрешённой работе, нужно разобрать точную причину и исправить правило, а не выключать всю защиту.

## Другие административные настройки

- В Settings → Advanced Security проверить доступные Secret Protection/уведомления об утечках и push protection. Публичное сканирование и видимые владельцу уведомления — разные настройки; файл политики не подтверждает их состояние.
- Включить **Private vulnerability reporting** и проверить появление **Report a vulnerability** в Security → Advisories у подходящего пользователя. Не отправлять настоящий токен в тестовом сообщении.
- Сохранить доступность уведомлений/обновлений Dependabot. Его PR проходят обычный CI; предложение обновления не означает автоматического одобрения.
- Ограничивать workflow-токен на уровне задач; календарный токен оставлять только для чтения. Не расширять права PAT ради обхода правила ветки. Значение, срок и права токена в этом ревью не просматривались.

Обновлять [SECURITY.md](../../SECURITY.md) подтверждёнными настройками только после проверки результата. Этот документ — инструкция и датированное наблюдение, не доказательство включённой защиты.
